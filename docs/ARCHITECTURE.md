# Архитектура

Один процесс `awgd` (Go, только стандартная библиотека) управляет туннелями через `awg-quick` и `awg`, которые собираются в образ из upstream `amneziawg-tools`; сам протокол реализует `amneziawg-go`.

```
cmd/awgd           точка входа: окружение, TLS, запуск серверов, автозапуск, остановка
internal/
  conf             разбор и строгая проверка .conf по ключам upstream 3.1, Sanitize (вырезание хуков
                   из конфигов подписки), генерация текста для awg-quick
  store            state.json и профили на диске (0600, атомарная запись)
  tunnel           up/down/status через awg-quick/awg без shell; интерфейс Runner для тестов
  subfetch         скачивание подписки: https, пин sha256//SPKI или хеш сертификата, ETag/304,
                   коды 403/404/429, запрет loopback/link-local, лимиты, MaskURL
  subsync          синхронизация профилей из подписок: Sanitize, откат, обход зависшего туннеля, планировщик
  auth             PBKDF2, сессии (хранятся хеши токенов), ограничитель попыток
  tlsutil          самоподписанный сертификат WebUI
  web              HTTP API, CSRF/CSP, встроенный UI (static/: index.html, app.css, app.js, шрифты), проба здоровья
  dnswire          разбор DNS-сообщений: вопрос, адреса из ответа, ответ-ошибка
  dns              DNS-форвардер: решения по политике, UDP/TCP/DoH, метки SO_MARK
  geo              базы geosite.dat / geoip.dat и текстовые списки, скачивание
  policy           правила PROXY/DIRECT/DROP, выученные из DNS адреса, таблица 210
  ros              интеграция с RouterOS 7: REST-клиент (пин, проверка .id), синхронизация address-list
                   и /ip/dns/static FWD по маркеру awg31, BGP-спикер (AS4, IPv4), Manager с расписанием
  failover         монитор резервирования: здоровье туннелей (рукопожатие, проба), выбор основного
  group            группы туннелей: балансировка (ECMP) и «по порядку», таблицы 150–169, основной выход = группа
  version          версия сборки (ldflags из файла VERSION)
```

## Потоки данных

- **Профиль.** `PUT /api/profiles/{name}` → `conf.Parse` (хуки и неизвестные ключи отвергаются) → `store.WriteProfile` (0600, атомарно).
- **Подъём.** `POST …/up` → `tunnel.Up`: повторный `conf.Parse`, `prepare` (в режиме шлюза `Table = 103` вместо таблицы профиля, без `DNS`; при выключенном IPv6 — без IPv6-адресов и маршрутов; MTU не ниже 1280 при IPv6), `Render` с хуками, сгенерированными приложением, запись в `RUN_DIR` (tmpfs), `awg-quick up`. Состояние «поднят» сохраняется для автозапуска.
- **Режим шлюза.** При старте `networkOptions` определяет LAN-интерфейс (маршрут по умолчанию или `AWG_LAN_IFACE`) и доступность IPv6, `EnsureRouting` ставит постоянные `ip rule priority 300 iif <LAN> lookup 103` и `blackhole default table 103 metric 254` (kill switch). Хуки туннеля добавляют NAT/NAT66 и MSS-clamp и восстанавливают правило; без kill switch правило снимается вместе с туннелем. Подготовку сети, которую Docker делает снаружи (sysctl, IPv6, ULA на veth), `entrypoint.sh` делает изнутри — так она работает и на RouterOS.
- **Несколько туннелей.** Каждый поднятый туннель получает свою таблицу (110–149, `Table` в рабочем конфиге) и правило `fwmark 0x310000NN → таблица` для пробы. Трафик LAN идёт в таблицу 103, где `default dev <основной>`; `SetPrimary` меняет этот маршрут одной командой. Первый поднятый туннель становится основным; при остановке основного трафик переходит на поднятый раньше других. Основной сохраняется в `state.json` и восстанавливается при автозапуске.
- **Резервирование.** `failover.Monitor` раз в `IntervalSec` читает `awg show`, считает возраст рукопожатия и делает TCP-пробу через каждый туннель (`SO_MARK` + `SO_BINDTODEVICE`). После `Threshold` неудач подряд туннель неисправен и получает паузу `CooldownSec`. Режим `standby` держит поднятыми все туннели из списка приоритета и переключает основной мгновенно, `switch` держит поднятым только основной и при сбое поднимает следующий. Возврат к более приоритетному — только после паузы и `Threshold` удачных проверок подряд.
- **Маршрутизация по правилам.** Трафик LAN сначала смотрит в таблицу 210 (`ip rule priority 250 iif <LAN>`): `PROXY` → `throw` (поиск продолжается в таблице 103, то есть в основном туннеле со всем резервированием и kill switch), `PROXY@туннель` → `dev туннель`, `DIRECT` → `via <шлюз LAN>` с MASQUERADE на LAN, `DROP` → `blackhole`, подключённые сети LAN → `throw`. При `default = direct` в таблице есть `default via <шлюз>`. Изменения применяются одной командой `ip -force -batch` с разницей от прошлого состояния (полная перезаливка только при первом применении или после ошибки).
- **DNS.** `dns.Server` на `:53` решает по `policy.MatchDomain`: `DROP` — NXDOMAIN, `DIRECT` — серверы «мимо VPN» без метки, `PROXY` — серверы «через VPN» с меткой `PrimaryMark` (правило `fwmark → 103`) или меткой таблицы указанного туннеля. Адреса из ответа на доменное правило попадают в `policy.Learn` и через 2 секунды — в таблицу 210.
- **Группы туннелей.** `group.Manager` держит группы из `state.json` (имя, режим `balance` или `ordered`, участники с весами). Каждой группе выделяется стабильная таблица 150–169 с `default` по исправным участникам: `balance` — `nexthop dev A weight w nexthop dev B weight w` (ECMP; `fib_multipath_hash_policy=1`, чтобы потоки делились по портам, а не по адресам), `ordered` — `dev` первого исправного. Здоровье даёт монитор резервирования (`Monitor.OnHealth`: туннель поднят, рукопожатие или проба в норме, пауза после сбоя закончилась). Состав пересчитывается после каждой проверки и после подъёма или остановки туннеля (`TunnelsChanged` принудительно перекладывает маршруты: ядро убирает ветки через исчезнувший интерфейс, даже если состав не изменился). Пустая группа получает `blackhole` через `route replace`, а не `route del`: `del default` без метрики мог бы снести и kill switch. Таблицы удалённых групп очищаются до укладки новых маршрутов, потому что новая (например, переименованная) группа занимает освободившуюся таблицу. Группа как основной выход — это `default` таблицы 103 (`applyGroupPrimaryLocked`); монитор не переключает такой основной и не опускает участников групп (`IsGroup`, `Keep`). `PROXY@группа` в таблице 210 получает маршрут группы через `policy.Nexthoper`, метка DNS «через группу» ведёт в её таблицу. IPv6 в группе идёт через одного участника.
- **Интеграция с RouterOS.** `ros.Manager` подписан на изменения политики (`policy.OnChange`) и синхронизирует не чаще раза в 10 секунд, а без изменений — раз в 5 минут. `policy.Export` отдаёт сети `PROXY` (CIDR и `geoip:`), выученные из DNS адреса со сроком и домены доменных правил и `geosite:`. Режим `address_list`: REST API (`/rest/.../print`, `PUT`, `PATCH`, `DELETE`) приводит список к нужному виду, трогая только записи с комментарием `awg31…`: сети — постоянные, адреса из DNS — с `timeout` (продлевается, когда осталось меньше половины). Режим `bgp`: контейнер сам подключается к роутеру на 179/tcp и анонсирует сети IPv4 с `NEXT_HOP` = свой IP; изменения уходят разницей (UPDATE и отзывы). `SyncDNS` добавляет записи FWD с `match-subdomain=yes` на IP контейнера. При выключении или смене списка управляемые записи удаляются.
- **Режим сервера.** Профиль с `ListenPort` и пирами без `Endpoint` (`conf.IsServer`) поднимается без своей таблицы: маршруты клиентов остаются в main, в режиме шлюза добавляется `MASQUERADE -o <LAN>`. Сервер никогда не становится основным и исключён из резервирования (`failover.Monitor.Exclude`).
- **Подписка.** `subsync.Sync` → `subfetch.Fetch` (только https, пин или проверка цепочки, `If-None-Match`). Если запрос не удался сетевой ошибкой, а поднятый туннель не отвечает дольше 180 с, туннель опускается и запрос повторяется напрямую. Ответ → `conf.Sanitize` (вырезание хуков и опасного `Table`, уведомление сохраняется в `Sub.LastNotice`) → `conf.Parse` → запись профиля. Туннель перезапускается, только если он был поднят и конфиг изменился; если новый не поднялся, возвращаются прежний профиль и туннель, а `ETag` не продвигается. В любом исходе опущенный ради обхода туннель поднимается обратно.
- **Статус.** `awg show interfaces` + `awg show <iface> dump` по каждому интерфейсу. Приватные ключи и PSK из вывода не читаются.

## Интерфейс

Статические файлы встроены через `//go:embed static` и отдаются без внешних зависимостей: `index.html` (одна точка входа `<div id="app">`), `app.css` (токены оформления панели: янтарный акцент, тёмные поверхности, радиусы 8/12/16/24), `app.js` и шрифты Exo 2 / JetBrains Mono в `static/fonts/` вместе с текстами лицензий OFL. Интерфейс собирается DOM API без `innerHTML` (значки: `DOMParser` для констант), поэтому CSP не содержит `unsafe-inline`. Язык (RU/EN) выбирается переключателем и хранится в `localStorage["awg31_lang"]`; словарь `I18N` обязан содержать одинаковые ключи в обоих языках. Тексты ошибок сервера пока только русские. Маршрутизация по хешу URL (`#/`, `#/profiles`, `#/new`, `#/p/<имя>[/config|/sub]`, `#/failover`, `#/policy`, `#/router`, `#/maintenance`), опрос статуса раз в 5 секунд без перерисовки при набранном вводе.

## Тестирование

Тесты — обычные `go test`. Внешние команды подменяются `tunnel.Runner`; HTTPS-серверы подписок поднимаются через `httptest`; сценарии отката и обхода зависшего туннеля идут через скриптуемый `Runner`. Каждая проблема из docs/SECURITY.md имеет собственный регрессионный тест, а версия в `VERSION` сверяется с README тестом. Помимо `go test`, защиты проверялись «мутациями»: копия проекта с одной сломанной защитой обязана провалить тесты.

Не покрыто автотестами: реальная сборка образа, `awg-quick` и iptables в живом ядре, запрос к настоящей панели. Интерфейс проверялся скриптом в настоящем Chrome (скриншоты в `docs/screenshots/`).
